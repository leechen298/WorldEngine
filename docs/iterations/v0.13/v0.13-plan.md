# v0.13 Minimum Runnable MVP Plan

Chinese mirror: `v0.13-plan.zh.md`.

Status: documentation preparation / active child 0.13.1

## Version Objective

Build and independently validate one deterministic, single-session,
single-Agent, lockstep vertical slice. The slice minimizes the depth of each
capability, not the number of links in the product loop.

The version is not complete until the same run is visible through the
administration console and Godot and is classified from public evidence by an
independent checker.

## Package 0.13.0: WorldEngine Runnable Anchor

Package name: `0.13.0-worldengine-runnable-anchor`

Status: closed / WorldEngine-side anchor verified

Type: mixed implementation package

Closeout note: all package-owned criteria passed current focused, E2E,
black-box, browser, and evaluator gates. Full backend regression remains
`484 passed, 1 failed` because of an unrelated dirty legacy assertion; this
package does not claim a clean repository-wide or complete-v0.13 PASS.

Goal: Implement the WorldEngine-side minimum runnable loop and administration
console behind a generic versioned client protocol.

Why this exists: The external client cannot validate a coherent world until
generation, session boot, lockstep runtime, Agent action, intervention
judgment, state evidence, and projection all share one canonical run.

Inputs / required reading:

- v0.13 parent documents.
- `docs/living-world-development-flow.zh.md`.
- project North Star, product model, scope boundaries, and iteration rules.
- current code only after implementation starts, as reuse inventory rather
  than design authority.

Allowed changes:

- Versioned generic HTTP schemas and capability manifest under the active
  `backend/app/` path.
- Deterministic structured world-package generation with a fixed seed.
- Session boot, lockstep step/run, rules, events, diffs, snapshots, public
  projection, and evidence export.
- Minimal public Agent perception/decision/action/result chain and bounded
  public experience link.
- Explicit intervention windows with one accepted bounded direction and one
  rejected direct-fact mutation path.
- A work-focused administration console under `frontend/` that uses the same
  APIs and never writes storage directly.
- Focused backend, frontend, and E2E tests.

Forbidden changes:

- No concrete anchor-world content in WorldEngine.
- No live-provider dependency, WebSocket requirement, production database,
  deployment, Godot project, or external repository changes.
- No raw thought, private memory, provider traces, or client-authored
  canonical patches.
- No implementation under `backend/worldengine/`.

Expected deliverables:

- `CapabilityManifest` and versioned control/runtime/evidence API.
- Deterministic `RunnableWorldPackage` with `package_hash`.
- Session state with monotonic `tick`, `revision`, and `state_hash`.
- Rule-linked Agent action and intervention evidence.
- Administration console for the complete WorldEngine-side flow.
- Focused tests and current review evidence.

Expected tests / verification:

- Deterministic package-hash tests.
- Session source-package and state-hash consistency tests.
- Exact lockstep tick-count tests.
- Agent causal-chain and second-decision experience-link tests.
- accepted/rejected intervention tests in the same explicit window.
- generic protocol black-box tests using only base URL and manifest.
- administration-console unit, build, and focused E2E smoke.

Compatibility constraints:

- The target contract is not derived from current API shapes.
- Prefer a new versioned public surface and adapters over silently changing
  existing responses.
- Existing dirty work must not be reverted or overwritten.
- Any reused implementation must pass the new tests without weakening the
  contract.

Scope guardrails:

- One fixed-seed world package, one session, one Agent, one meaningful state
  variable, one rule-driven action, and two interventions are sufficient.
- The actual concrete world stays external.
- `0.13.0` must not claim complete MVP PASS because Godot and external checker
  evidence belong to later packages.

Exit criteria:

- Documentation and contract evaluator has no P1/P2 findings.
- User authorizes implementation for this package only.
- Focused backend/frontend/E2E checks pass with current evidence.
- Generic black-box client can complete the WorldEngine-side flow.
- Package review records no unresolved P1/P2 and hands off the stable contract
  bundle to `0.13.1`.

Handoff to next package: Publish the versioned manifest, schemas, example
requests, and evidence contract for the external repository without copying
concrete external fixtures into WorldEngine.

## Package 0.13.1: Godot Validation Client Anchor

Package name: `0.13.1-godot-validation-client-anchor`

Status: planned / documentation preparation only

Type: mixed external-repository package

Current authorization: documentation preparation only. Implementation,
external repository changes, Godot/checker execution, and evidence execution
remain unauthorized until the complete external milestone is reviewed and
explicitly approved.

Goal: Adapt `WorldEngine-Validation-Client` into a minimal Godot 2D scenario
executor plus an independently runnable checker.

Why this exists: A headless API and Web administration console do not prove
that a game engine can consume the generic contract, maintain projection
consistency, return typed feedback, and produce independent evidence.

Inputs / required reading:

- reviewed `0.13.0` public manifest/schema/evidence bundle.
- external repository `AGENTS.md` and active milestone rules.
- archived scenario/evidence/checker documents that remain compatible with
  v0.13 after review.

Allowed changes:

- Create a Godot project/package inside the external repository.
- Store one concrete fixed-seed anchor world and visual mappings externally.
- Add a scenario runner that connects through the public manifest and HTTP
  protocol.
- Add an isolated checker package/process that consumes exported evidence and
  Godot operation records.
- Freeze the previous Web UI/API implementation as legacy; selectively migrate
  only reviewed scenario, evidence, and result-contract assets.
- Use a separated run layout where the executor writes only `raw/`, a sealed
  artifact manifest records hashes, and the checker alone writes `verdict/`.

Forbidden changes:

- No changes to WorldEngine from this external package.
- No direct database access, internal Python imports, canonical state patches,
  provider calls, private memory, raw thought, or executor self-certification.
- No checker reinterpretation of canonical world facts or event legality; it
  evaluates only whether public evidence supports suite assertions.
- No per-frame WorldEngine synchronization, polished game, or broad rewrite of
  every old milestone.

Expected deliverables:

- Minimal Godot 2D executor.
- External anchor scenario and projection mapping.
- Operation log with request IDs, session/tick/revision/state hashes, and
  screenshots or frame evidence where useful.
- Independent checker and result-directory contract.
- Checker-generated `run_id`/nonce, clean-run directory, `seal.json`, complete
  public-response hashes, and negative mutation fixtures.
- External repository tests and review evidence.

Expected tests / verification:

- Godot project starts and renders nonblank state.
- Executor discovers WorldEngine from public manifest only.
- Dashboard and Godot report the same session/revision/state hash and
  intervention outcomes.
- Godot submits at least one typed action or feedback request.
- Checker rejects missing, mismatched, self-asserted, or stale evidence.
- Checker rejects tampered hashes, reused run IDs, non-monotonic ticks, crossed
  session IDs, sensitive output, and prewritten PASS results.

Compatibility constraints:

- Old Web/API code may remain frozen during the first migration.
- Historical result directories are non-current and cannot satisfy v0.13.
- The executor and checker may share schema files, but not execution state or
  a success flag.
- The existing v0.9.1 README/review status mismatch must be repaired in the
  external milestone before implementation authorization.

Scope guardrails:

- One 2D scene, one Agent projection, one meaningful object/state, and basic
  controls are enough.
- No third repository in v0.13.
- Do not turn the external scenario into a source for core abstractions.

Exit criteria:

- External milestone documents are reviewed before implementation.
- Godot and checker run as separate processes/packages.
- External focused tests pass and no P1/P2 finding remains.
- A result candidate can be handed to `0.13.2` without a PASS claim.

Handoff to next package: Provide a fresh operation/evidence directory with all
required correlation IDs and no prefilled final classification.

## Package 0.13.2: Anchor Run Validation And Closeout

Package name: `0.13.2-anchor-run-validation-and-closeout`

Status: planned / documentation package required

Type: validation and closeout package

Goal: Execute the complete anchor run from clean startup and classify the
minimum runnable MVP from current public evidence.

Why this exists: Passing component tests or starting the Godot scene does not
prove that generation, runtime, Agent behavior, user intervention, projection,
and validation form one causal world history.

Inputs / required reading:

- reviewed closeout evidence from `0.13.0` and `0.13.1`.
- current WorldEngine and external validation repository revisions.
- anchor scenario assertion matrix and result-directory contract.

Allowed changes:

- Validation-only repairs that receive their own reviewed child package.
- Clean-run scripts, evidence capture, checker execution, and closeout docs.
- Human visual checkpoint after automated evidence collection.

Forbidden changes:

- No implementation repair hidden inside closeout.
- No reuse of stale v0.10-v0.12 or earlier external result directories.
- No manual override from `FAIL`/`BLOCKED` to `PASS`.
- No private-state or UI-only evidence as the authoritative result.

Expected deliverables:

- Clean-run environment and revision manifest.
- WorldEngine evidence bundle.
- Godot operation and visual evidence.
- Per-assertion checker report with evidence references.
- Final `PASS`, `PARTIAL`, `BLOCKED`, or `FAIL` closeout.

Expected tests / verification:

- Generate the fixed-seed package and verify `package_hash` handoff.
- Run exact bounded ticks and validate monotonic state.
- Validate Agent causal chain and prior-experience-linked second decision.
- Submit accepted and rejected interventions in the same open window.
- Compare Dashboard and Godot session/revision/state hashes.
- Run checker negative controls against tampered or missing evidence.

Compatibility constraints:

- Results apply only to the recorded WorldEngine and external repository
  revisions.
- `BLOCKED` is reserved for an unexecutable required dependency; executed
  behavior or evidence mismatch is `FAIL`.
- Missing evidence never becomes PASS.

Scope guardrails:

- Closeout validates only the minimum anchor scenario.
- Findings outside the anchor contract become later roadmap work.
- A polished product or general intelligence claim is forbidden.

Exit criteria:

- Every assertion has status and evidence references.
- Negative controls prove the checker can fail bad evidence.
- Human checkpoint confirms the Godot projection is coherent without becoming
  the authoritative oracle.
- Final classification and unresolved findings are recorded in both
  repositories.

Handoff to next package: After a PASS, deepen world quality, Agent continuity,
additional clients, or persistence through new reviewed versions. After
`PARTIAL`, `BLOCKED`, or `FAIL`, route the concrete cause to a new scoped repair
package.

# v0.3 计划

状态：`已规划 / 进行中`

## 版本名称

WorldSpec Loader and Runtime Bridge

中文含义：WorldSpec 加载器与运行时桥接。

## 目标

v0.3 要把 WorldEngine 从 v0.2 的递归世界结构基础，推进到“通用
`WorldSpec` 可以被加载、校验，并以受控方式进入运行时上下文”的阶段。
这个版本的重点不是让 Agent 生活在世界里，也不是验证生成世界的质量，而是
先把世界数据接近运行时所需的边界、契约、最小实现和兼容性证据建立起来。

核心判断标准：

- `WorldSpec` 是否可以作为通用世界输入进入核心代码。
- 已加载的世界数据是否可以变成运行时上下文。
- `RuntimeEngine` 的旧行为是否仍然兼容。
- 后续外部验证是否可以只依赖公开契约，而不是依赖核心代码内部细节。

## 版本边界

v0.3 可以定义或实现：

- WorldSpec 加载器契约。
- 最小通用 WorldSpec 加载器。
- 运行时上下文桥接契约。
- 最小可选运行时上下文桥接层。
- 运行时、API、事件、归档、参数、前端可见行为和旧路径兼容性证据。
- 外部验证样例运行器契约准备。
- 证据索引和兼容性审计。
- 发布候选文档和最终收口文档。

v0.3 不可以实现：

- 世界内 Agent 闭环。
- 记忆或自我连续性基座。
- 世界生成。
- 面向外部产品界面的投影 API。
- 产品 UI 或游戏 UI。
- 具体演示世界样例。
- 具体外部验证世界。
- 外部样例仓库。
- 外部验证仓库。
- 剧情生成。
- NPC 聊天系统。
- 自我意识声明。

## 兼容性基线要求

任何后续 v0.3 迭代包，只要准备修改运行时、API、事件、归档、参数、
前端可见行为或旧路径行为，就必须先在当前会话中提供兼容性证据。证据至少
覆盖：

- `RuntimeEngine` 的 tick 行为和 `world_time_seconds` 行为。
- API 包装格式和错误形状。
- `/runtime/step`。
- `/world/events`。
- `/world/event-steps`。
- 世界参数和参数应用行为。
- 归档快照和摘要行为。
- 可选 `Event.refs` 的响应兼容性。
- 前端可见响应形状。
- 旧目录 `backend/worldengine/` 的边界。

这条基线的意思是：后续不是不能改运行时，而是不能在没有证据的情况下改。
每个会影响旧行为的包，都要先证明“现在的旧行为是什么”，再说明“本包是否
改变它、如何验证没有破坏它”。

## 进度判断方式

v0.3 的进度应按基础设施能力判断，而不是按最终产品体验判断：

- 加载器相关包证明：通用 `WorldSpec` 数据可以安全进入核心代码。
- 桥接层相关包证明：已加载的世界数据可以成为运行时上下文，同时不替换或
  破坏 v0.1 运行时脚手架。
- 外部验证准备包证明：后续验证可以使用公开契约，而不是依赖核心代码内部
  私有细节。
- 证据和发布包证明：兼容性、范围和交付状态都能被复查。

v0.3 不证明生成世界质量，不证明 Agent 可以在世界中生活，也不证明外部产品
已经有用。这些判断从后续版本开始。

## 防跑偏规划标准

后续每个 v0.3 迭代包都必须描述工作应该怎么推进，不能只写允许改什么文件。
如果实现者仍然需要从零判断下面这些问题，就说明该包规格还不够细：

- 新代码或新契约应该放在哪里。
- 数据从输入到输出如何流动。
- 哪些现有行为是只读的兼容性表面。
- 哪些测试能证明本包没有越界。
- 哪些看起来顺手的相邻能力必须留到后续版本。

下面每个包里的“实现 / 设计路径”是规划护栏，不代表 0.3.0 允许开始写代码，
也不替代后续每个包自己的已评审契约。

### 0.3.4 Runtime Context Bridge Implementation

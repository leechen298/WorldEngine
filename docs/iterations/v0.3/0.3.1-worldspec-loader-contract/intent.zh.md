# 意图

## 问题

v0.2 已经把 `WorldSpec` 定义为 schema 对象，但还没有定义 WorldEngine 应该
如何把 `WorldSpec` 数据加载进当前代码边界。如果没有经过评审的加载器契约，
第一次实现很容易在写代码时临时发明输入形式、错误语义、fixture 策略或运行时
权限。

## 目标

创建可评审的加载器契约，定义后续最小加载器实现所需的输入、输出、错误类别、
校验行为、领域中立示例策略和兼容性边界。

## 非目标

- 不实现加载器。
- 不把已加载数据连接到 `RuntimeEngine`。
- 不新增 API 路由或响应形状。
- 不新增持久化、归档、参数、事件或前端行为。
- 不创建具体 `WorldSpec` fixture 数据。
- 不创建外部 fixture 或验证仓库。
- 不实现世界生成、世界内 Agent 闭环、记忆、自我连续性、投影、剧情生成或
  NPC 聊天行为。

## 为什么现在做

v0.3 的目标是让通用 `WorldSpec` 数据在保持 v0.1 兼容的前提下接近运行时
上下文。加载器是这条路径的第一个边界，因此必须在 `0.3.2` 写代码前先明确
契约。

## North Star 对齐

本包为结构化世界规格进入 WorldEngine 准备通用路径，支持项目北极星。它让
核心保持领域中立，并避免加载器工作在桥接契约评审前变成演示专用、应用专用
或拥有运行时权力的实现。

## 假设

- 在后续已评审包改变前，`WorldSpec` 仍是 v0.3 加载器校验的 schema 来源。
- 初始加载器即使不连接运行时，也有独立价值。
- 后续实现包可以允许文件形式的 JSON 输入，但只能作为通用来源形式。

## 未解决风险

- 错误路径格式可能受校验库影响，除非实现层做规范化。
- 文件加载如果处理不当，可能被误扩展成 fixture 目录或外部仓库。
- 后续桥接层可能需要更多元数据，但本包保持加载器元数据中立，且不赋予运行时
  权力。

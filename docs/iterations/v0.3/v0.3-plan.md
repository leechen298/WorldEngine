# v0.3 Plan

Status: planned / in progress

## Version Name

WorldSpec Loader and Runtime Bridge

## Objective

Move WorldEngine from the v0.2 recursive schema foundation toward validated
generic WorldSpec loading and runtime context bridging while preserving v0.1
runtime compatibility.

## Version Boundaries

v0.3 may define or implement:

- WorldSpec loader contract.
- minimal generic WorldSpec loader.
- runtime context bridge contract.
- minimal optional runtime context bridge.
- runtime/API/event/archive/params/frontend-facing/legacy-path compatibility
  evidence.
- external fixture runner contract readiness.
- evidence and compatibility audit.
- release-candidate and final closeout docs.

v0.3 must not implement:

- Agent-in-World loop.
- memory or self-continuity substrate.
- world generation.
- projection API for external product surfaces.
- product UI or game UI.
- concrete demo world fixture.
- concrete external validation world.
- external fixture repository.
- external validation repository.
- story generation.
- NPC chat system.
- self-awareness claims.

## Required Compatibility Baseline

Before any future v0.3 package changes runtime, API, event, archive, params,
frontend-facing, or legacy-path behavior, that package must provide
current-session compatibility evidence for:

- `RuntimeEngine` tick and `world_time_seconds` behavior.
- API envelope and error shape.
- `/runtime/step`.
- `/world/events`.
- `/world/event-steps`.
- world params and params apply behavior.
- archive snapshot and summary behavior.
- optional `Event.refs` response compatibility.
- frontend-facing response shapes.
- legacy `backend/worldengine/` boundary.

## Progress Evaluation Model

v0.3 progress should be judged by infrastructure capability, not by final
product experience:

- Loader packages prove that generic WorldSpec data can enter the core safely.
- Bridge packages prove that loaded world data can become runtime context
  without replacing or breaking the v0.1 runtime scaffold.
- External fixture readiness proves that future validation can use public
  contracts instead of private core internals.
- Evidence and release packages prove that compatibility and scope claims are
  reviewable.

v0.3 does not prove that generated worlds are high quality, that Agents can
live in those worlds, or that an external product is useful. Those claims start
in later versions.

## Anti-Drift Planning Standard

Every future v0.3 package must describe how the work should be approached, not
only what files may change. A package is under-specified if an implementer
would still need to decide any of these from scratch:

- where the new code or contract belongs.
- how data moves from input to output.
- which existing behavior is read-only compatibility surface.
- which tests prove the package stayed inside scope.
- which tempting adjacent feature must wait for a later version.

The package approach sections below are planning rails. They are not permission
to implement code during 0.3.0, and they do not override the reviewed contract
for each future package.

### 0.3.1 WorldSpec Loader Contract

Package name: `0.3.1-worldspec-loader-contract`

Status: planned

Type: documentation-only

Goal: Define the WorldSpec loader contract before implementing loader code.

Why this exists: Loader implementation needs a reviewed contract for inputs,
outputs, error model, validation behavior, and domain-neutral fixture policy
before code can safely load WorldSpec data.

Implementation / design approach:

- Define the loader as a data-boundary component that receives generic
  WorldSpec input and returns either validated data or structured errors.
- Specify accepted input forms, such as parsed objects, in-memory dictionaries,
  or file-backed data, only if they remain domain-neutral.
- Define output shape without giving it runtime authority; loaded data is not a
  running world yet.
- Separate parse errors, schema validation errors, and unsupported-input errors.
- Define a neutral example policy using abstract identifiers only.
- Explicitly state that RuntimeEngine, API routes, persistence, and world
  generation are outside this contract.

- Create 0.3.1 package docs.
- Define loader input, output, error, and validation semantics.
- Define domain-neutral example policy without adding concrete fixture data.
- Define compatibility expectations for keeping loader separate from runtime.

Forbidden changes:

- Do not implement loader.
- Do not connect loader to runtime.
- Do not create concrete WorldSpec fixture data.
- Do not create an external fixture repository.
- Do not change API routes or response shapes.
- Do not modify RuntimeEngine behavior.

Scope guardrails:

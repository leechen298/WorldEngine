# 意图

## 问题

`0.3.2` 实现了通用 `WorldSpec` 加载器，`0.3.3` 定义了运行时上下文
桥接契约。但运行时仍没有已评审的方式来持有已加载的世界上下文。如果没有
边界明确的实现包，桥接工作可能会意外改变 tick 行为、暴露原始
`WorldSpec` 数据、把 `WorldCell` 重新解释为 `WorldModule`，或扩展到
生成、Agent、记忆、投影、产品特定行为。

## 目标

实现最小的可选运行时上下文桥接：只接受成功的加载器输出或已评审的等价
输入，派生有界惰性上下文，并默认保持既有运行时和公共行为不变。

## 非目标

- 不迁移 `RuntimeEngine` 到 `WorldCell`。
- 不让上下文影响 `RuntimeEngine.step()`、`world_time_seconds`、模块执行、
  事件、参数、归档快照或 API 响应。
- 不添加新的 API 路由或前端行为。
- 不持久化运行时上下文。
- 不修改 schema 或 migration。
- 不创建 fixture 或具体世界数据。
- 不实现世界生成、Agent-in-World 循环、记忆、自连续性、投影、故事生成或
  NPC 聊天行为。
- 不修改遗留 `backend/worldengine/` 运行时代码。

## 为什么现在做

v0.3 的目标是在不丢失 v0.1 兼容性的前提下，把已验证的通用
`WorldSpec` 数据推向运行时。本包是在加载器和桥接契约经过评审之后的最小
实现步骤。

## 北极星对齐

该桥接通过让已验证的世界规格数据成为可检查的运行时上下文，支持
WorldEngine 作为通用递归世界运行时基底。它避免演示专用逻辑，并把未来
Agent、记忆、生成和投影行为留给后续里程碑。

## 假设

- `backend/app/core/worldspec_loader.py` 中的 `LoadedWorldSpec` 是正常桥接
  输入。
- 运行时上下文首先作为惰性元数据和诊断信息就是有价值的。
- 既有 `RuntimeEngine` 构造调用必须在不传入上下文时继续工作。
- 既有默认模块树仍然是 v0.3 运行时行为的权威基线。
- 除非本包评审明确批准新增诊断路径，否则任何上下文 API 暴露都需要后续
  已评审包。

## 开放风险

- 向 `RuntimeEngine` 添加上下文存储可能意外泄露到序列化运行时响应。
- 如果只运行单元测试，可能无法充分覆盖前端可见响应兼容性。
- 错误归一化可能重复加载器的验证职责。
- 复制到上下文中的元数据若不保持中性，可能变成领域特定含义。

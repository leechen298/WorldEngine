# 意图

## 问题

`0.3.1` 已定义 WorldSpec 加载器契约，但 WorldEngine 还没有实现能够接收通用
`WorldSpec` 输入，并返回已校验加载结果或结构化加载错误的组件。如果没有限定
范围的实现包，加载器代码可能意外获得运行时权限、临时发明 fixture 策略，或
提前混入未来运行时桥接工作。

## 目标

新增满足 `docs/contracts/worldspec-loader-contract.md` 的最小加载器实现和聚焦
测试。

完成后，加载器应能：

- 接收受支持的领域中立输入形式。
- 通过现有 `WorldSpec` schema 校验数据。
- 成功时返回中立来源元数据。
- 在不支持输入、解析失败、schema 校验失败，以及实现文件输入时的文件 I/O
  失败场景返回稳定结构化错误。
- 通过测试证明没有运行时、API、事件、持久化、归档、参数或前端副作用。

## 非目标

- 不把已加载数据连接到 `RuntimeEngine`。
- 不定义或实现运行时上下文桥接语义。
- 不新增 API 路由、服务端点、持久化模型、归档写入、参数应用、事件发出、
  前端行为、fixture 或迁移。
- 不创建具体演示世界或外部验证世界输入数据。
- 不实现世界生成、世界内 Agent 闭环、记忆、自我连续性、投影、剧情生成或
  NPC 聊天行为。

## 为什么现在做

v0.3 要用小而可评审的步骤，把 v0.2 的 `WorldSpec` schema 基础推向运行时
上下文。在 `0.3.3` 定义已加载数据如何进入运行时上下文前，加载器必须先存在
并有测试证明。

## North Star 对齐

本包为结构化世界规格创建领域中立的数据入口，支持 WorldEngine 作为通用递归
世界引擎的发展。它保留规格加载与运行时执行之间的边界，让应用专用世界和外部
验证内部细节继续留在核心仓库之外。

## 假设

- `0.3.1-worldspec-loader-contract` 已完成评审，仍是规范性加载器契约。
- `backend/app/schemas/world_cell.py` 中的 `WorldSpec` 仍是本包的校验来源。
- 最小加载器即使在运行时桥接前也有价值，因为它能独立建立已校验数据和错误
  语义。
- 文件 JSON 输入是可选的；如果不实现文件输入，除说明文件输入不受支持外，
  不要求实现 `io_error` 行为。

## 未解决风险

- Pydantic 错误结构可能暴露超过公共加载器契约所需的细节；实现必须规范化错误，
  避免依赖私有格式。
- 文件输入如果不限制为单个调用方提供的 JSON 文档，可能扩展成 fixture 目录。
- 来源标签可能意外携带领域含义；测试和文档必须保持标签中立。
- 未来桥接工作可能需要更多元数据，但本包不得预先设计运行时上下文字段。

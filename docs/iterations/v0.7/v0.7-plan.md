# v0.7 Plan

Status: final / closeout complete

## Version Name

External Validation Readiness / Projection Consumer Readiness

## Objective

Make WorldEngine ready for external validation suites and projection consumers
through public contracts, redacted reports, consumer-facing projection
boundaries, readiness manifests, and compatibility evidence while preserving
WorldEngine as a generic recursive world generation and runtime engine.

v0.7 must turn v0.6 generation and runtime evidence into reviewable public
readiness surfaces. It must not import private external validation worlds,
external application behavior, or projection-product implementation into the
core repository.

## Version Boundaries

v0.7 may define or implement:

- external validation readiness concepts and public contract surfaces.
- redacted validation report schema, report validation, and evidence archive
  rules.
- projection consumer contracts for read-only runtime, event, Agent loop,
  memory-summary, and generation-readiness payloads.
- contract bundle and readiness manifest export paths for external suites.
- generic quality regression and compatibility evidence across public engine
  contracts.
- focused backend, API, frontend, E2E, Agent smoke, autonomous saved-result,
  and compatibility checks only after reviewed child packages authorize them.
- release-candidate, final closeout, and post-closeout evidence documents.

v0.7 must not implement:

- the first external projection application; v0.8 owns that scope.
- concrete external validation worlds or fixtures inside this repository.
- concrete world names, maps, characters, locations, resources, story rules,
  seed data, private transcripts, UI selectors, hidden reset APIs, or private
  validation oracle behavior.
- application-specific backend logic or product packaging flows.
- live provider behavior, generated-world persistence, or subjective
  generation-quality approval unless a later reviewed version owns those
  scopes.
- durable persistence or migrations unless a reviewed v0.7 child explicitly
  authorizes them.
- new runtime features under `backend/worldengine/`.
- external suite PASS, projection application readiness, product readiness, or
  full autonomous runner/full-suite PASS claims without current-session
  evidence.

## Required Compatibility Baseline

Before any implementation-bearing v0.7 child changes runtime, schema, API,
event, archive, params, frontend-facing, test, checker, fixture, migration, or
legacy behavior, that child must provide current-session evidence for the
touched surface and focused regression evidence for adjacent compatibility
surfaces.

Compatibility-sensitive surfaces include:

- `WorldSpec`, `WorldCell`, and `EntityRef`.
- `load_worldspec`, `LoadedWorldSpec`, `WorldSpecLoaderResult`, and
  `WorldSpecLoaderError`.
- `RuntimeContext`, `RuntimeContextSummary`, `build_runtime_context`, and
  `summarize_runtime_context`.
- `RuntimeEngine.get_runtime_context`, `RuntimeEngine.step`, tick/time
  behavior, event emission, and runtime-context non-leakage.
- `PerceptionFrame`, `ActionIntent`, `ActionResult`, request-scoped
  `LoopStep`, and `POST /world/agent/loop/step`.
- v0.5 working/episodic memory context surfaces.
- v0.6 world generation request, template, plan, preview, regeneration, and
  runtime-readiness surfaces.
- API envelope and error shape.
- `/runtime/state`, `/runtime/step`, `/world/events`, `/world/event-steps`,
  `/world/agent/params/propose-and-apply`, `/world/agent/loop/step`, archive
  behavior, and `/world/generation/*`.

Schema and API changes must be additive unless the active child contract
explicitly allows a breaking change.

## Codex `/goal` And Evaluator Model

`完成 v0.7` uses `GOAL_RUNNER.md`, `CURRENT_STATE.md`, and
`CAMPAIGN_PLAN.md`. Implementation-bearing children require documentation /
contract evaluator, implementation-scope evaluator, code-review evaluator,
validation-evidence evaluator, and closeout consistency review before
closeout.

Documentation-only children that change goal routing, evidence rules, package
sequencing, automation-consumption contracts, release status, validation
templates, report schemas, projection contracts, or mirror obligations require
a read-only documentation evaluator.

If evaluator tooling is unavailable or not authorized, the package must remain
`planned / ready for review` or record the blocker. It must not silently claim
review complete.

The parent roadmap does not create active child contracts. Future child package
documents may revise the order, split, merge, or defer planned packages when
review evidence shows the parent roadmap is incomplete or unsafe.

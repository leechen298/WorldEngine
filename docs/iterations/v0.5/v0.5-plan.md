# v0.5 Plan

Status: final / closeout complete

## Version Name

Memory And Self-Continuity Substrate

## Objective

Move WorldEngine from the v0.4 request-driven Agent-in-World loop toward the
first inspectable memory and self-continuity substrate while preserving v0.4
loop compatibility and keeping generation, external validation readiness, and
projection application readiness out of scope.

## Version Boundaries

v0.5 may define or implement:

- working memory records with provenance, bounded lifetime semantics, and
  inspectable sources.
- episodic memory records linked to events, ticks, world time, and action
  outcomes.
- relationship state schema semantics.
- self-summary schema semantics.
- reflection record schema semantics.
- personality drift signal schema semantics.
- a first generic in-memory substrate only after a reviewed child package
  authorizes implementation.
- bounded read-only memory context for the Agent Loop only after a reviewed
  child package authorizes integration.
- focused backend tests and compatibility evidence for touched surfaces.
- evidence audit, release-candidate, and final closeout docs.

v0.5 must not implement:

- world generation; v0.6 owns that scope.
- external validation runner readiness or report automation; v0.7 owns that
  scope.
- projection application readiness; v0.8 owns that scope.
- concrete world names, maps, characters, locations, resources, story rules,
  seed data, UI-specific app behavior, or private validation oracle details.
- frontend product behavior unless a later reviewed v0.5 child explicitly
  authorizes it.
- durable persistence or migrations unless a later reviewed v0.5 child
  explicitly authorizes it.
- new runtime features under `backend/worldengine/`.

## Capability Boundary Split

| Capability | v0.5 docs contract | First implementation package |
| --- | --- | --- |
| Working memory | define concept, provenance, bounded read/write semantics | yes: additive schema + generic in-memory substrate |
| Episodic memory | define event-linked episode semantics | yes: additive schema + generic in-memory substrate |
| Relationship state | define schema semantics only | no behavior yet |
| Self-summary | define schema semantics only | no summarization behavior yet |
| Reflection records | define schema semantics only | no automatic reflection yet |
| Personality drift signals | define schema semantics only | no action modifier yet |

## Public Interface Intent

`0.5.0` does not add public runtime APIs or implementation files.

Planned future implementation interfaces may include:

- planned schema module: `backend/app/schemas/agent_memory.py`.
- planned service/store module: `backend/app/agent/memory.py` or an
  equivalent approved path.
- planned tests: `backend/app/tests/test_agent_memory_*.py`.
- bounded additive extensions to `PerceptionFrame` only after
  `0.5.3-memory-context-loop-integration` is reviewed and authorized.

## Required Compatibility Baseline

Before any implementation-bearing v0.5 child changes runtime, schema, API,
event, archive, params, frontend-facing, test, fixture, migration, or legacy
behavior, that child must provide current-session evidence for the touched
surface and focused regression evidence for adjacent compatibility surfaces.

Compatibility-sensitive surfaces include:

- `PerceptionFrame`.
- `ActionIntent`.
- `ActionResult`.
- request-scoped `LoopStep`.
- `POST /world/agent/loop/step`.
- `/world/agent/params/propose-and-apply`.
- runtime tick and world time behavior.
- API envelope and error shape.
- `/runtime/state`, `/runtime/step`, `/world/events`, and
  `/world/event-steps`.
- world params and params apply behavior.
- archive behavior.
- `Event.refs` optional serialization.

Schema changes must be additive unless the active child contract explicitly
allows a breaking change.

## Codex `/goal` And Subagent Model

`完成 v0.5` uses `GOAL_RUNNER.md`, `CURRENT_STATE.md`, and
`CAMPAIGN_PLAN.md`. Implementation-bearing children require documentation /
contract evaluator, implementation-scope evaluator, code-review evaluator,
validation-evidence evaluator, and closeout consistency review before closeout.

Documentation-only children that change goal routing, evidence rules, package
sequencing, automation-consumption contracts, release status, validation
templates, or mirror obligations require a read-only documentation evaluator.

# v0.6 Plan

Status: in progress / 0.6.0 review complete

## Version Name

World Generation v1

## Objective

Move WorldEngine from reviewed `WorldSpec` loading, runtime-context bridging,
Agent-in-World loop, and memory substrate toward the first generic world
generation capability. v0.6 must generate valid, runnable `WorldSpec` data from
templates and structured AI-assisted generation plans, with validation,
metadata, preview, and regeneration support.

## Version Boundaries

v0.6 may define or implement:

- generation request and result contracts.
- generic template semantics and a deterministic template generator core.
- structured generation plan validation and compilation into `WorldSpec`.
- provider-independent AI-assisted generation boundaries where model output is
  a structured plan to validate.
- generation metadata, provenance, diagnostics, preview, and regeneration
  semantics.
- backend schemas, services, API routes, frontend preview UI, and focused
  tests only after reviewed child packages authorize them.
- evidence audit, release-candidate, and final closeout docs.

v0.6 must not implement:

- external validation runner readiness or report automation; v0.7 owns that
  scope.
- first external projection application readiness; v0.8 owns that scope.
- concrete world names, maps, characters, locations, resources, story rules,
  seed data, UI-specific app behavior, or private validation oracle details.
- durable persistence or migrations unless a reviewed v0.6 child explicitly
  authorizes them.
- live external AI-provider behavior unless a reviewed child explicitly
  authorizes provider configuration, security, failure handling, and tests.
- new runtime features under `backend/worldengine/`.
- full autonomous validation, external validation readiness, projection
  readiness, or product readiness claims.

## Capability Boundary Split

| Capability | v0.6 docs contract | First implementation package |
| --- | --- | --- |
| Generation request/result | define public schema semantics | yes: backend schema/service |
| Generic templates | define template shape and constraints | yes: deterministic template core |
| Structured generation plan | define compiler contract | yes: plan compiler |
| AI-assisted generation | define provider-independent plan import | yes: mock/import boundary only |
| Metadata/provenance | define required evidence fields | yes: generation result metadata |
| Preview | define bounded inspectable output | yes: backend/API then dashboard |
| Regeneration | define input lineage and constraints | yes: bounded regeneration service |
| External validation readiness | explicitly out of scope | no, v0.7 |
| Projection app readiness | explicitly out of scope | no, v0.8 |

## Public Interface Intent

`0.6.0` does not add public runtime APIs or implementation files.

Planned future implementation interfaces may include:

- planned schema module: `backend/app/schemas/world_generation.py`.
- planned service module: `backend/app/world/generation.py` or an equivalent
  approved path.
- planned API route: `backend/app/api/routes/world_generation.py`.
- planned tests: `backend/app/tests/test_world_generation_*.py`.
- planned frontend surfaces: `frontend/src/components/GenerationPanel.vue`,
  `frontend/src/api/client.ts`, and focused component/E2E tests only after a
  reviewed child authorizes frontend work.

These paths are not authorized until the relevant child package review records
`implementation_authorized: yes`.

## Required Compatibility Baseline

Before any implementation-bearing v0.6 child changes runtime, schema, API,
event, archive, params, frontend-facing, test, fixture, migration, or legacy
behavior, that child must provide current-session evidence for the touched
surface and focused regression evidence for adjacent compatibility surfaces.

Compatibility-sensitive surfaces include:

- `WorldSpec`, `WorldCell`, and `EntityRef`.
- `load_worldspec`, `LoadedWorldSpec`, `WorldSpecLoaderResult`, and
  `WorldSpecLoaderError`.
- `RuntimeContext`, `RuntimeContextSummary`, `build_runtime_context`, and
  `summarize_runtime_context`.
- `RuntimeEngine.get_runtime_context`, `RuntimeEngine.step`, tick/time
  behavior, event emission, and runtime-context non-leakage.
- `PerceptionFrame`, `ActionIntent`, `ActionResult`, request-scoped
  `LoopStep`, and `POST /world/agent/loop/step`.
- v0.5 working/episodic memory context surfaces.
- API envelope and error shape.
- `/runtime/state`, `/runtime/step`, `/world/events`, `/world/event-steps`,
  `/world/agent/params/propose-and-apply`, and archive behavior.

Schema changes must be additive unless the active child contract explicitly
allows a breaking change.

## Codex `/goal` And Evaluator Model

`完成 v0.6` uses `GOAL_RUNNER.md`, `CURRENT_STATE.md`, and
`CAMPAIGN_PLAN.md`. Implementation-bearing children require documentation /
contract evaluator, implementation-scope evaluator, code-review evaluator,
validation-evidence evaluator, and closeout consistency review before
closeout.

Documentation-only children that change goal routing, evidence rules, package
sequencing, automation-consumption contracts, release status, validation
templates, or mirror obligations require a read-only documentation evaluator.

If evaluator tooling is unavailable or not authorized, the package must remain
`planned / ready for review` or record the blocker. It must not silently claim
review complete.

Package name: `0.6.10-v0.6-final-closeout`

Status: planned

Type: documentation-only

Goal: Mark v0.6 final / closeout complete only after release-candidate
approval, evidence consistency checks, status synchronization, and unresolved
finding classification.

Why this exists: Final closeout must be a separate evidence-backed decision,
not an automatic result of implementation completion.

Inputs / required reading:

- `0.6.9` release-candidate bundle and review.
- All v0.6 child reviews.
- Current git status and command evidence required by final closeout.
- `docs/roadmap.md` and status surfaces.

Allowed changes:

- Final closeout docs and status surfaces authorized by the package.
- Roadmap/status sync only after evidence supports final status.

Forbidden changes:

- Do not modify implementation files.
- Do not add new generation behavior.
- Do not claim v0.7 external validation readiness, v0.8 projection readiness,
  concrete product readiness, or unrun validation.

Expected deliverables:

- Final closeout record.
- Parent status updates.
- Review evidence with commands, scope, compatibility, and unresolved findings.
- Handoff to v0.7 only after final closeout evidence passes.

Expected tests / verification:

- Documentation checks and scope guard.
- Fresh implementation/regression evidence required by final closeout
  contract.
- Status consistency checks.
- Closeout consistency evaluator, if authorized and available.

Compatibility constraints:

- Final status must match README, roadmap/status surfaces if touched, current
  state, and review evidence.
- Final evidence must distinguish v0.6 generation readiness from v0.7 external
  validation and v0.8 projection readiness.

Scope guardrails:

- Stop on stale status drift, missing evidence, or unresolved P1/P2.
- Stop if final closeout tries to expand scope beyond reviewed v0.6 packages.

Exit criteria: v0.6 can be marked `final / closeout complete` only after final
review approval and evidence consistency checks pass.

Handoff to next package: none inside v0.6. The next handoff is to the next
version only after final closeout.

Handoff to next version: v0.7 external validation readiness / projection
consumer readiness may start only from its own reviewed iteration package.

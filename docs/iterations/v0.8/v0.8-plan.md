# v0.8 Plan

Status: planned / ready for review

## Version Name

Minimum Proved Working WorldEngine / External Validation Readiness

## Objective

Prepare WorldEngine's core-side contracts, public observable surfaces, and
evidence boundaries so a separate external validation function can verify that
WorldEngine reaches a minimum normally working state.

v0.8 must not implement the external validator or the first external product
application in this repository. It must make the core engine coherent and
observable enough for external validation while keeping validation scenarios,
connection details, oracle logic, concrete app data, and product-specific
behavior outside the core repository.

## Planning Authority Boundary

This file is the v0.8 parent roadmap and planned package specification. The
`0.8.x` sections below are route-map specs only. They are not active child
contracts, implementation authorization, evidence execution authorization, or
closeout evidence.

Before any `0.8.x` child starts, the agent must create or confirm that child's
complete document set at that time, then pass its review gate. If
implementation reveals a design gap, stop implementation, update the current
child's `contract.md`, `technical-design.md`, `test-plan.md`, `plan.md`, and
`review.md`, and continue only after the updated package is reviewed.

Post-closeout v0.7 code review in
`docs/testing/results/2026-06-02-v0.7-code-review.md` recorded blocking
findings. v0.8 packages must either repair affected dependency surfaces with
current-session evidence under an authorized package, route a narrow v0.7
repair first, or record those findings as blockers. They must not silently use
v0.7 closeout as clean pass, minimum working-state PASS, or external
validation readiness PASS.

## Version Boundaries

v0.8 may define or implement after reviewed child authorization:

- minimum normally working WorldEngine claim semantics.
- core-side observable public surfaces for external validation.
- generation -> runtime -> Agent loop readiness boundaries.
- bounded memory-context and event evidence requirements.
- additive, generic read-only projection/read-model APIs or payload helpers.
- external-validation handoff contract fields that identify public surfaces,
  evidence references, redaction status, and blockers.
- provider-boundary, credential, mock fallback, or gated live-smoke semantics
  only when the active child explicitly owns that scope.
- core-side smoke and compatibility evidence tied to public engine contracts.
- evidence audit, release-candidate, and final closeout documents.

v0.8 must not implement:

- the external validation function.
- the external projection application or first product application.
- product-specific UI, routing, packaging, deployment, application state, or
  backend logic.
- concrete app worlds, names, maps, locations, characters, resources, story
  rules, seed data, private transcripts, UI selectors, hidden reset APIs,
  private oracle behavior, private runner state, private external repo paths,
  provider traces, or secrets.
- external validation PASS, external consumer PASS, product readiness, runtime
  PASS, API PASS, frontend PASS, E2E PASS, Agent smoke PASS, autonomous PASS,
  or generation-quality PASS without current-session evidence.
- durable persistence, migrations, live provider behavior, active generated
  world runtime execution, or new runtime features under `backend/worldengine/`
  unless the active child explicitly authorizes that scope.

## Public Interface Intent

The parent v0.8 documentation package does not add public runtime APIs,
schemas, checker code, frontend routes, or implementation files.

Planned future interfaces may include:

- planned minimum working-state contract under `docs/contracts/`.
- planned core observable surface contract under `docs/contracts/`.
- planned external-validation handoff manifest or report shape under an
  approved `docs/contracts/` or `docs/testing/` path.
- planned checker or helper code under an approved test/checker path only
  after package review records `implementation_authorized: yes`.
- planned backend/API read-only projection endpoints only after a reviewed
  package proves they are generic engine contracts, not product-app or
  external-validator behavior.

These paths are not authorized until the relevant child package review records
`implementation_authorized: yes` or explicitly authorizes documentation-only
contract changes.

## Required Compatibility Baseline

Before any implementation-bearing v0.8 child changes runtime, schema, API,
event, archive, params, frontend-facing, test, checker, fixture, migration, or
legacy behavior, that child must provide current-session evidence for the
touched surface and focused regression evidence for adjacent compatibility
surfaces.

Compatibility-sensitive surfaces include:

- v0.7 external validation report schema/checker semantics.
- v0.7 readiness manifest schema/checker semantics.
- v0.7 projection consumer contract and projection read-model schema/checker
  semantics.
- `WorldSpec`, `WorldCell`, and `EntityRef`.
- `load_worldspec`, runtime-context bridge, and `RuntimeEngine` compatibility.
- runtime state, event timeline, archive, params, Agent loop, memory context,
  and generation readiness public surfaces.
- API envelope and error shape.
- `/runtime/state`, `/runtime/step`, `/world/events`, `/world/event-steps`,
  `/world/agent/loop/step`, archive routes, and `/world/generation/*`.

Schema and API changes must be additive unless the active child contract
explicitly allows a breaking change.

## Codex `/goal` And Evaluator Model

`完成 v0.8` uses `GOAL_RUNNER.md`, `CURRENT_STATE.md`, and
`CAMPAIGN_PLAN.md`. Implementation-bearing children require documentation /
contract evaluator, implementation-scope evaluator, code-review evaluator,
validation-evidence evaluator, and closeout consistency review before closeout.

Documentation-only children that change process rules, package sequencing,
evidence rules, automation-consumption contracts, release status, validation
templates, report schemas, projection contracts, readiness taxonomy, or mirror
obligations require a read-only documentation evaluator.

If evaluator tooling is unavailable or not authorized, the package must remain
`planned / ready for review` or record the blocker. It must not silently claim
review complete.

# v0.5 整体功能测试计划

Status: proposed / not executed
Date: 2026-05-31
Scope: WorldEngine 截止 v0.5 的整体功能、E2E、Codex/Agent 测试方案

## 一句话结论

v0.5 的核心不是完整自主 Agent、外部验证 readiness、持久化记忆系统或新的
projection 应用；它是在 v0.4 request-driven Agent Loop 上增加第一层可审计的
memory/self-continuity substrate：

```text
WorkingMemoryRecord / EpisodicMemoryRecord
  -> InMemoryAgentMemoryStore
  -> PerceptionFrame.memory_context
  -> existing Agent Loop action semantics unchanged
```

所以 v0.5 测试要分成三类看：

- 后端/API 确定性验证：这是 v0.5 memory substrate 和 loop 集成的核心通过依据。
- Browser E2E：当前 `agent-loop-step` E2E 能回归 v0.4 loop API，但没有公开 memory seed/write API，不能证明非空 memory context 的端到端 UI/API 场景。
- Codex/Agent 测试：当前 Agent smoke 和 minimal autonomous saved-result checker 验证 dashboard 现有产品基线，不等于 v0.5 in-world memory 或完整自主 Agent PASS。

本文件是测试文档产物，不是 PASS verdict。任何通过结论必须来自后续当前会话命令或 checker 结果。

## v0.5 功能边界

### 必须纳入整体测试

| 功能切面 | 需要证明什么 | 主要验证入口 |
| --- | --- | --- |
| `WorkingMemoryRecord` | required fields、provenance、priority、bounded lifetime 字段语义可序列化且验证严格 | `test_agent_memory_substrate.py` |
| `EpisodicMemoryRecord` | event/action/outcome refs、tick、world time、source、summary 语义可审计 | `test_agent_memory_substrate.py` |
| `InMemoryAgentMemoryStore` | 按 `agent_id` + `world_id` 隔离，排序 deterministic，limit 边界正确 | `test_agent_memory_substrate.py` |
| 读隔离 | add/list 返回值不能暴露可变 backing state | `test_agent_memory_substrate.py`、`test_agent_perception.py` |
| `PerceptionFrame.memory_context` | perception 中只读、bounded、additive 地包含 working/episodic memory | `test_agent_perception.py` |
| Loop API memory context | `POST /world/agent/loop/step` 在 store 有记录时返回 memory context，且默认 action 仍为 noop | `test_agent_loop_api.py` |
| v0.4 action 兼容 | `noop`、`params.patch`、rejected action、strict 422 envelope 行为不变 | `test_agent_loop_service.py`、`test_agent_loop_api.py`、`test_agent_action_adapter.py` |
| 邻接兼容 | runtime、event、params、archive、API envelope、`Event.refs` 未被 memory 集成破坏 | focused compatibility tests、full backend regression |
| 文档与证据一致性 | v0.5 final status 不夸大未运行的 E2E、Agent smoke、自主验证、外部验证、projection readiness | docs scan、`git diff --check`、人工 review |

### 明确不是 v0.5 通过标准

这些内容不能作为 v0.5 必须通过项，只能记录为 deferred scope、future coverage 或有意未覆盖：

- durable persistence、migration、数据库 memory store。
- public memory API、memory seed API、memory write endpoint。
- vector retrieval、semantic search、embedding。
- automatic reflection、self-summary generation、relationship behavior。
- personality drift action modifier 或让 memory 改变 action choice。
- world generation；属于 v0.6。
- external validation runner readiness / report automation；属于 v0.7。
- projection application readiness；属于 v0.8。
- 具体世界、地图、角色、地点、资源、故事规则、seed data、私有 validation oracle。
- 完整 background autonomy 或 full autonomous runner/full suite。

## 推荐执行顺序

### 0. 执行前冻结状态

```bash
git status --short --branch
git diff --stat
```

测试报告必须记录：

- 当前分支。
- 当前 commit 或候选工作树状态。
- 是否包含未提交变更。
- 这是验证当前工作树、某个 commit，还是 release candidate。

### 1. 依赖检查

```bash
make check-backend
make check-frontend
```

失败处理：

- backend venv 缺失时先运行 `make setup-backend`。
- frontend `node_modules` 缺失时先运行 `make setup-frontend`。
- 依赖缺失是环境阻塞，不是 v0.5 功能失败。

### 2. v0.5 memory substrate focused 验证

在 `backend/` 目录执行：

```bash
.venv/bin/python -m pytest app/tests/test_agent_memory_substrate.py -q
```

通过标准：

- working-memory required semantics 验证通过。
- missing `updated_at` 等 schema 错误能被 Pydantic 拒绝。
- store 按 agent/world scope 隔离。
- working memory 按 priority、updated time、`memory_id` deterministic 排序。
- episodic memory 按 tick、world time、`memory_id` deterministic 排序。
- `limit=0` 返回空列表。
- add/list 不暴露 mutable backing state。

### 3. v0.5 memory loop integration focused 验证

在 `backend/` 目录执行：

```bash
.venv/bin/python -m pytest app/tests/test_agent_perception.py app/tests/test_agent_loop_api.py -q
```

通过标准：

- `PerceptionBuilder` 没有 memory store 时保持旧调用兼容。
- 有 memory store 时返回 bounded `memory_context`。
- `memory_context.working_memory` 和 `memory_context.episodic_memory` 只包含目标 agent/world 记录。
- 修改 perception 返回对象不会污染 store。
- `POST /world/agent/loop/step` 返回 additive `perception.memory_context`。
- 默认 loop 仍返回 deterministic `noop`，不因 memory context 改变 action semantics。

### 4. v0.5 loop/action 邻接兼容验证

在 `backend/` 目录执行：

```bash
.venv/bin/python -m pytest app/tests/test_agent_memory_substrate.py app/tests/test_agent_perception.py app/tests/test_agent_loop_service.py app/tests/test_agent_loop_api.py app/tests/test_agent_action_adapter.py -q
```

通过标准：

- memory substrate 和 perception 集成测试通过。
- v0.4 `noop`、`params.patch`、unsupported action、invalid patch、strict 422 envelope 行为继续通过。
- `/world/agent/loop/step` response shape additive，不破坏旧字段。

### 7. Browser E2E 基线

在仓库根目录执行：

```bash
make test-e2e
```

或只运行 Agent Loop API E2E：

```bash
cd frontend && pnpm exec playwright test e2e/agent-loop.spec.ts
```

通过标准：

- PASS 只能来自 Playwright assertion 当前会话退出 `0`。
- `agent-loop-step` 覆盖 bounded perception、params patch、rejected action、schema errors、event evidence。
- dashboard E2E 覆盖 runtime、params、invalid params、agent autotune、timeline、archive summary。

重要边界：

- 当前 `agent-loop-step` E2E 没有断言非空 `memory_context`，因为没有公开 memory seed/write API。
- dashboard `MemoryPanel` 是 archive summary UI，不是 v0.5 in-world agent memory UI。
- E2E 基线通过不能单独证明 v0.5 memory substrate 完整通过；它只能证明公开 API 和 dashboard 没被破坏。

### 8. 建议新增 v0.5 memory-context E2E

当前不能直接把这个场景标成 executable。它需要先经过迭代包批准，提供公开 seed/setup contract 或测试专用 fixture hook，且不能把外部世界或私有 validation oracle 放进核心仓库。

建议场景：

| 场景名 | 前置条件 | 输入 | 断言 |
| --- | --- | --- | --- |
| `agent-loop-memory-context-api` | E2E server 能以 generic fixture 向 `agent.default` / `world.default` 注入 memory store | `POST /world/agent/loop/step` | response 含 bounded `memory_context`，默认 action 仍 `noop` |
| `agent-loop-memory-context-scope-api` | 注入同 world 不同 agent、同 agent 不同 world 的 memory | `POST /world/agent/loop/step` | 只返回目标 agent/world 记录 |
| `agent-loop-memory-context-readonly-api` | 注入 memory 后执行 rejected/accepted action | loop 调用前后查询 seed state 或 checker snapshot | loop 不修改 memory store |

落点建议：

- scenario contract: `docs/testing/e2e-scenarios/agent-loop-memory-context.md`
- implementation: `frontend/e2e/agent-loop-memory-context.spec.ts`
- durable result: `docs/testing/results/YYYY-MM-DD-v0.5-agent-loop-memory-context-e2e.md`

在这些场景实现并运行前，只能标为 proposed / not executed。

### 9. Basic Agent smoke

Basic Agent smoke 是 Codex 作为测试操作者，通过 UI/CLI 操作 dashboard；PASS 必须由 deterministic checker 给出。

可执行入口：

```bash
make validate-agent-smoke-fixtures
make validate-agent-smoke-result RESULT_DIR=test-results/agent-smoke/<timestamp>
```

已支持 checker 的场景包括：

- `dashboard-basic-runtime`
- `dashboard-params-flow`
- `dashboard-invalid-param`
- `dashboard-agent-autotune`

每次 live run 必须产出：

```text
test-results/agent-smoke/<timestamp>/
├── result.json
├── operation-log.jsonl
├── transcript.md
├── console.log
├── api-summary.json
└── screenshots/
```

运行约束：

- `operation-log.jsonl` 只能记录 `ui` 和 `cli` operation。
- 直接 API 调用不能作为 Agent operation。
- API 状态只能由 helper/checker 写进 `api-summary.json`。
- `result.json.verdict_source` 必须是 `deterministic_checker`。
- Codex 的自然语言总结不能替代 checker verdict。

注意：Agent smoke 覆盖 dashboard 基线，不覆盖 v0.5 in-world memory/self-continuity 行为。

### 10. Minimal autonomous saved-result checker

可执行入口：

```bash
make validate-agent-autonomous-fixtures
make validate-agent-autonomous-result RESULT_DIR=test-results/agent-autonomous/<timestamp>
```

通过标准：

- checker 退出 `0`。
- `result.json.verdict_source` 或等价 evidence 指向 scorecard checker。
- raw artifacts 包含 result、operation log、scorecard summary、transcript、console log、screenshots。
- negative fixture 能拒绝 agent self-verdict、direct API operation、CLI nonzero、unresolved P1、failed score item、missing artifact。

边界：

- 这只能证明某个 saved-result directory 被 checker 接受。
- 它不是 full autonomous runner/full suite PASS。
- 它不证明 v0.5 memory context 被 autonomous agent live-run 覆盖。

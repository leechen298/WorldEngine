## Findings

### P1: `source_label` redaction misses common secret formats

File: `backend/app/core/world_generation.py`

Lines: `_public_core_readiness_source_label()` at lines 824-837, called from
`check_core_readiness()` at lines 663-664.

Impact: `POST /world/generation/core-readiness` accepts arbitrary
`source_label` values and then returns the redacted-or-original label through
`runtime_readiness.runtime_context_summary.source_label` and
`agent_loop_probe.perception.runtime_context_summary.source_label`. The current
marker list redacts path/private/repo/secret/token/credential values, but it
does not redact common secret-looking labels such as `api-key-*`,
`password=*`, `bearer *`, or `sk-live-*`.

Evidence probe:

```bash
PYTHONPATH=backend backend/.venv/bin/python -c '<source_label redaction probe>'
```

Result:

```text
api-key-abc123 True api-key-abc123
password=abc123 True password=abc123
bearer abc123 True bearer abc123
sk-live-abc123 True sk-live-abc123
credential-abc123 False redacted
token-abc123 False redacted
repo-abc123 False redacted
```

Contract risk: the package contract requires returned evidence to be redacted,
and the technical design says the response must not expose secrets, provider
traces, or private data. This public API can still echo secret-looking labels
as public readiness evidence.

Suggested direction: treat `source_label` as untrusted public evidence input.
Either always replace caller-provided labels with a stable public identifier,
or expand redaction to cover key/password/bearer/sk-style patterns and add
table-driven tests for those formats.

Repair status: repaired in the follow-up change. Secret-like labels including
`api-key-*`, `password=*`, `bearer *`, and `sk-live-*` now redact before being
returned through runtime-readiness or Agent-loop probe evidence.

### P2: Agent-loop evidence returns full perception events instead of a summary

File: `backend/app/core/world_generation.py`

Lines: `agent_loop_probe=AgentLoopProbeEvidence(...)` at lines 792-796.

Impact: `agent_loop_probe.perception` is populated with
`loop_response.perception.model_dump(mode="json")`, which includes full
`recent_events` objects. Those objects include event payloads and timestamps.
The separate `isolated_events` field is correctly reduced to id/tick/time/type
/source, but the Agent perception path reintroduces the full event object.

Evidence probe:

```bash
PYTHONPATH=backend backend/.venv/bin/python -c '<agent perception event-shape probe>'
```

Result excerpt:

```text
dict_keys(['id', 'tick_id', 'world_time_seconds', 'type', 'source', 'payload', 'created_at'])
{'payload': {'step_seconds': 600, 'updated_at': '...', 'params': {}}}
```

Contract risk: the technical design allows bounded event ids/types/ticks from
isolated events plus an Agent perception summary. Returning the full perception
object is broader than the approved evidence shape and creates a future leak
risk if isolated params or event payloads become non-empty.

Suggested direction: build an explicit Agent-loop evidence DTO for the probe:
runtime summary, bounded event references without payload, runtime-context
summary, optional bounded memory summary, intent type/reason, and result
status/applied. Avoid dumping the whole `PerceptionFrame`.

Repair status: repaired in the follow-up change. The core-readiness
`agent_loop_probe.perception` evidence now uses a bounded summary rather than
dumping the full `PerceptionFrame`; recent events contain only id, tick,
world time, type, and source.

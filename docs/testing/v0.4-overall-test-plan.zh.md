# v0.4 整体功能测试计划

Status: proposed / not executed
Date: 2026-05-31
Scope: WorldEngine 截止 v0.4 的整体功能、E2E、Codex/Agent 测试计划

## 一句话结论

v0.4 的核心不是完整自主 Agent，也不是新的前端产品体验；它是一个最小、请求驱动的 Agent-in-World 闭环：

```text
PerceptionFrame -> ActionIntent -> validation/apply -> ActionResult -> LoopStepResponse
```

所以测试要分成三类看：

- 后端/API 确定性验证：这是 v0.4 当前最强、最直接的通过依据。
- Browser E2E：当前已有 dashboard E2E 基线，但 v0.4 新 loop 没有前端入口；若要覆盖新 loop，应先做 API-level Playwright E2E，UI-level E2E 等 dashboard 暴露入口后再做。
- Codex 自主测试：当前可执行的是 basic Agent smoke；完整 scorecard-based autonomous 只有契约骨架，不能宣称 PASS，必须先补 checker 和 result schema。

## v0.4 功能边界

### 必须纳入整体测试

| 功能切面 | 需要证明什么 | 主要验证入口 |
| --- | --- | --- |
| `PerceptionFrame` | 从 runtime state、recent events、world params、runtime context summary 构建感知帧 | `test_agent_perception.py`、`test_agent_loop_service.py`、`POST /world/agent/loop/step` |
| 感知只读性 | 构建 perception 不修改 runtime、event log、world params | `test_agent_perception.py`、服务级测试 |
| `ActionIntent` / `ActionResult` | 只接受 v0.4 最小动作词表并返回可审计结果 | `test_agent_action_adapter.py`、`test_agent_loop_api.py` |
| `noop` | 无副作用；带 patches 时必须 rejected | `test_agent_action_adapter.py`、`test_agent_loop_api.py` |
| `params.patch` | 复用现有 param validation、dry-run、apply 语义 | `test_agent_action_adapter.py`、params 兼容测试 |
| `AgentLoopService` | 一次 request-scoped perceive -> intent -> validate/apply -> result | `test_agent_loop_service.py` |
| 新 API | `POST /world/agent/loop/step` envelope、状态变更、事件证据正确 | `test_agent_loop_api.py`、建议新增 API-level Playwright |
| 旧 API 兼容 | `/world/agent/params/propose-and-apply` 仍可用 | `test_params_agent.py`、`test_agent_loop_api.py` |
| 运行时兼容 | runtime tick/time、event API、params API、archive、legacy boundary 不被破坏 | focused compatibility tests、full backend regression、现有 E2E |
| 文档与证据一致性 | v0.4 status、review、evidence 不夸大未运行测试 | docs scan、`git diff --check`、人工 review |

### 明确不是 v0.4 通过标准

这些内容不能作为 v0.4 必须通过项，只能记录为未来范围或有意未覆盖：

- memory、episodic memory、relationship state、self-summary、reflection、personality drift；这些属于 v0.5。
- world generation；属于 v0.6。
- external validation runner readiness / report automation；属于 v0.7。
- projection application readiness；属于 v0.8。
- 具体世界、地图、角色、地点、资源、故事规则、seed data、私有 validation oracle。
- background autonomy；v0.4 是 request-driven，不是后台自主 Agent runtime。
- UI-level v0.4 Agent Loop；当前没有 dashboard 入口，不能要求 browser UI E2E 覆盖这个新 loop。

## 推荐执行顺序

### 0. 执行前冻结状态

执行测试前先记录当前分支和工作树，避免把未固定的本地变化当作稳定基线。

```bash
git status --short --branch
git diff --stat
```

如果工作树有未提交变化，测试报告必须写清楚：

- 当前分支。
- 是否包含未提交 v0.4 实现或文档变更。
- 是否只是在验证候选工作树，而不是已合入基线。

### 1. 依赖检查

```bash
make check-backend
make check-frontend
```

失败处理：

- backend venv 缺失时先运行 `make setup-backend`。
- frontend `node_modules` 缺失时先运行 `make setup-frontend`。
- 不要把依赖缺失写成测试失败；它是环境阻塞。

### 2. v0.4 后端/API focused 验证

在 `backend/` 目录执行：

```bash
.venv/bin/python -m pytest app/tests/test_agent_perception.py app/tests/test_agent_action_adapter.py app/tests/test_agent_loop_service.py app/tests/test_agent_loop_api.py -q
```

通过标准：

- perception 包含 runtime、params、recent events、runtime context summary。
- 默认 loop 返回 deterministic `noop`。
- 有效 `params.patch` 返回 accepted、更新 params、写入 `params.applied`。
- unsupported action、invalid patch、noop with patches 均 rejected 且无 mutation。
- schema 错误走 422 envelope，未知字段不被静默丢弃。

### 3. v0.4 邻接兼容验证

在 `backend/` 目录执行：

```bash
.venv/bin/python -m pytest app/tests/test_agent_loop_service.py app/tests/test_agent_loop_api.py app/tests/test_params_agent.py app/tests/test_event_api_compat.py app/tests/test_runtime_step.py -q
```

通过标准：

- 新 `/world/agent/loop/step` route 正常。
- 旧 `/world/agent/params/propose-and-apply` route 正常。
- runtime step、event API、params 相关兼容表面未破坏。

### 4. 后端全量回归

在 `backend/` 目录执行：

```bash
.venv/bin/python -m pytest app/tests tests -q
```

通过标准：

- 命令退出 `0`。
- 报告记录 pass count、耗时、失败用例名。
- 若失败，先按失败模块分类；不要直接说 v0.4 loop 失败，除非失败指向 v0.4 代码或测试。

### 5. 前端单元测试和构建

v0.4 没有改 frontend，但“截止 v0.4 整体功能”建议跑一次前端基线，证明 dashboard 没被后端/API 变化间接破坏。

在 `frontend/` 目录执行：

```bash
pnpm test
pnpm build
```

通过标准：

- vitest 退出 `0`。
- build 退出 `0`。
- 若 Vite 仍有历史 chunk-size warning，记录为 warning，不当作失败，除非出现新的构建错误。

### 6. 当前 Browser E2E 基线

在仓库根目录执行：

```bash
make test-e2e
```

当前已实现的 E2E 场景：

- `dashboard-basic-runtime`
- `dashboard-params-flow`
- `dashboard-invalid-param`
- `dashboard-agent-autotune`
- `dashboard-timeline-navigation`
- `dashboard-archive-summary`

通过标准：

- PASS 只能来自 Playwright assertion 当前会话退出 `0`。
- 不从 Codex 视觉观察或人工描述得出 PASS。
- artifact 保留在 `test-results/e2e/artifacts/`。
- HTML report 保留在 `test-results/e2e/html-report/`。

重要边界：

- 这些场景证明现有 dashboard 功能仍可用。
- 它们不证明 v0.4 新 Agent Loop API 已经有 UI-level E2E 覆盖。

### 7. 建议新增 v0.4 API-level Playwright E2E

因为 v0.4 新 loop 没有前端入口，推荐先新增 API-level Playwright 场景。它仍使用 Playwright runner 和 webServer，但通过 `request` 访问公开 API。

建议场景：

| 场景名 | 输入 | 断言 |
| --- | --- | --- |
| `agent-loop-noop-api` | `POST /world/agent/loop/step` 空 body | `intent.type=noop`、`result.status=noop`、params 不变、无新 `params.applied` |
| `agent-loop-params-patch-api` | `params.patch counter.increment=4` | HTTP 200、accepted、`/world/params` 更新、`/world/events` 有 `source=agent.loop` |
| `agent-loop-invalid-patch-api` | reserved path，例如 `runtime.secret` | HTTP 200、rejected、params 不变、无 `params.applied` |
| `agent-loop-unsupported-action-api` | `type=world.spawn` | HTTP 200、rejected、`reason=unsupported_action`、无 mutation |
| `agent-loop-schema-422-api` | extra field 或 `event_limit=0` | HTTP 422、API envelope `code=30`、params 不变 |
| `agent-loop-old-agent-compat-api` | 调用旧 params-agent route | 旧 route 仍返回成功或既有预期结果 |

落点建议：

- scenario contracts: `docs/testing/e2e-scenarios/agent-loop-api.md`
- implementation: `frontend/e2e/agent-loop-api.spec.ts`
- durable result: `docs/testing/results/YYYY-MM-DD-v0.4-agent-loop-api-e2e.md`

在这些场景实现并运行前，只能把它们标为 proposed / not executed，不能写成 passed。

### 8. Basic Agent smoke

Basic Agent smoke 是 Codex 作为测试操作者，通过 UI/CLI 操作 dashboard；PASS 必须由 deterministic checker 给出。

可执行入口：

```bash
make validate-agent-smoke-fixtures
make validate-agent-smoke-result RESULT_DIR=test-results/agent-smoke/<timestamp>
```

已支持 checker 的场景：

- `dashboard-basic-runtime`
- `dashboard-params-flow`
- `dashboard-invalid-param`

每次 live run 必须产出：

```text
test-results/agent-smoke/<timestamp>/
├── result.json
├── operation-log.jsonl
├── transcript.md
├── console.log
├── api-summary.json
└── screenshots/
```

运行约束：

- `operation-log.jsonl` 只能记录 `ui` 和 `cli` operation。
- 直接 API 调用不能作为 Agent operation。
- API 状态只能由 helper/checker 写进 `api-summary.json`。
- `result.json.verdict_source` 必须是 `deterministic_checker`。
- Codex 的总结不能替代 checker verdict。

建议 v0.4 整体回归至少执行：

- `dashboard-basic-runtime`：证明 Codex 能打开 dashboard 并推进 runtime。
- `dashboard-params-flow`：证明 Codex 能通过 UI 改 params 并触发后续事件。
- `dashboard-invalid-param`：证明 Codex 能通过 UI 触发错误，checker 证明 params 不变。

注意：Agent smoke 覆盖 dashboard 基线，不覆盖 v0.4 in-world Agent loop 的完整自主行为。

### 9. Broader Codex autonomous 测试门槛

当前 `docs/testing/agent-autonomous/` 只有 `contract-only-do-not-execute` 场景。要运行完整 autonomous，必须先补一个独立实现包，至少交付：

- autonomous result schema。
- scorecard schema。
- scorecard checker。
- Makefile 入口，例如 `make validate-agent-autonomous-result RESULT_DIR=<dir>`。
- scenario runner 或明确的操作记录格式。
- forbidden operation 检查。
- required artifacts 检查。
- unverified P1/P2/P3 规则。

建议未来 raw artifact 目录：

```text
test-results/agent-autonomous/<timestamp>/
```

建议 durable summary：

```text
docs/testing/results/YYYY-MM-DD-v0.4-agent-autonomous-contract-review.md
docs/testing/results/YYYY-MM-DD-v0.4-agent-autonomous-run.md
```

在 checker 存在前，报告必须写：

```text
broader autonomous: not run / blocked - missing scorecard checker
```

不能写：

```text
broader autonomous passed
```

## Stop conditions

立即停止并记录 blocker 的情况：

- v0.4 文档和代码范围不一致，无法判断当前候选状态。
- dependency check 失败且依赖不能安装。
- backend focused tests 失败。
- full backend regression 失败且失败指向 v0.4 或兼容表面。
- Playwright 无法启动服务，且不是已知 sandbox/端口环境问题。
- Agent smoke artifact 缺失、operation log 包含 direct API operation、或 verdict source 是 `agent`。
- broader autonomous 被要求运行，但 scorecard checker 仍不存在。

## 推荐优先级

如果目标是“现在马上验证 v0.4 候选是否靠谱”，按这个优先级执行：

1. L1 + L2：v0.4 backend/API focused tests 和 full backend regression。
2. L3：现有 `make test-e2e`，确认 dashboard 基线未破。
3. L5：basic Agent smoke 三个已支持场景中至少跑 `dashboard-basic-runtime`，理想情况下补跑 params-flow 和 invalid-param。
4. L4：新增 API-level Playwright 后再跑 v0.4 loop E2E。
5. L6：另开后续包实现 autonomous checker 后，再谈完整 Codex autonomous PASS。
